## 1. Source of truth (API contract)

This prompt is **bounded to the actual API**. Do not invent features the API cannot support.

### Base URL

```
http://localhost:3001
```

### Endpoint matrix

| Method | Path                   | Purpose                          |
| ------ | ---------------------- | -------------------------------- |
| GET    | `/api/tasks`            | List tasks (filters + pagination) |
| POST   | `/api/tasks`            | Create a task                     |
| GET    | `/api/tasks/:id`        | Get one task                      |
| PUT    | `/api/tasks/:id`        | Full update of a task             |
| PATCH  | `/api/tasks/:id/status` | Move a task to its next status    |
| DELETE | `/api/tasks/:id`        | Delete a task                     |

### Real Task data model (Mongoose schema)

| Field         | Type                            | Notes                       |
| ------------- | ------------------------------- | --------------------------- |
| `_id`         | string (Mongo ObjectId)         | generated by DB             |
| `title`       | string — **required**           | trimmed, non-empty          |
| `description` | string — default `""`           |                             |
| `status`      | enum `todo` / `doing` / `done`  | default `todo`              |
| `priority`    | enum `low` / `medium` / `high`  | default `medium`            |
| `dueDate`     | ISO date or `null`              | due date, optional          |
| `createdAt`   | ISO datetime (timestamp)        | auto                        |
| `updatedAt`   | ISO datetime (timestamp)        | auto                        |

### Query parameters — `GET /api/tasks`

| Param      | Values                          | Notes                              |
| ---------- | ------------------------------- | ---------------------------------- |
| `status`   | `todo` \| `doing` \| `done`     | filter by status                    |
| `priority` | `low` \| `medium` \| `high`     | filter by priority                  |
| `search`   | string (also `title` alias)     | case-insensitive title search       |
| `page`     | integer (default `1`)           | pagination page                     |
| `limit`    | integer 1–100 (default `10`)    | items per page                      |
| `sortBy`   | `createdAt` \| `dueDate` (default `createdAt`) | sort field            |
| `order`    | `asc` \| `desc` (default `desc`) | sort direction                     |

### Response envelopes

- **Success collection:** `{ success: true, data: Task[], pagination: { page, limit, total, totalPages, hasNextPage, hasPrevPage } }`
- **Success single/create/update:** `{ success: true, message: "...", data: Task }`
- **Success delete:** `{ success: true, message: "Task deleted successfully" }`
- **Error:** `{ success: false, message: "...", statusCode, details: [...] }`

### Key API behaviours (must be reflected in the UI)

1. **Status is only allowed to move forward:** `todo → doing → done`, one step at a time (the server enforces this). The UI must disable / not show invalid "next" transitions.
2. `title` is required & non-empty; the UI must validate this before submitting.
3. `_id`, `createdAt`, `updatedAt` are **server-controlled** — never editable in forms.
4. Filters, search, sort, and pagination are all **server-side** (via query params), never client-side.
5. Swagger / OpenAPI docs are exposed at `/api-docs`.

## BEGIN PROMPT

You are a senior product UI/UX designer and frontend engineer. Your task is to **generate the complete, production-ready user interface and frontend application** for a **Task Management System** backed by a REST API. Return a detailed design that includes: **feature map, page architecture, screen-by-screen wireframes, component inventory, design system (colors, typography, spacing), interaction spec, API wiring per screen, and a recommended frontend tech stack** aligned with the API.

### 1. Product definition

Design a **Task Management web application** that lets the user:

1. **View** all tasks with advanced filtering (by `status`, by `priority`, by search text), sorting, and pagination.
2. **Create** a new task with Title (required), Description, Priority, and Due Date.
3. **Open** a task detail view.
4. **Edit** any editable task field.
5. **Advance** a task's status through the valid forward-only flow: `todo → doing → done`.
6. **Delete** a task (with a confirmation step before any destructive action).

### 2. Data model & API contract (MUST match exactly)

Base URL: `http://localhost:3001`

Task fields and constraints (read carefully):

- `title` — string, **required**, non-empty
- `description` — string, optional (may be empty)
- `status` — enum: `todo` | `doing` | `done` (default `todo`)
- `priority` — enum: `low` | `medium` | `high` (default `medium`)
- `dueDate` — ISO 8601 datetime or `null`
- `createdAt` / `updatedAt` — ISO 8601 timestamps (server-managed)
- `id` — Mongo ObjectId string

Endpoints:

1. `GET /api/tasks` — list. Query params: `status`, `priority`, `search` (substring, case-insensitive), `page` (default `1`), `limit` (1–100, default `10`), `sortBy` (`createdAt` | `dueDate`, default `createdAt`), `order` (`asc` | `desc`, default `desc`). Response: `{ success, data: Task[], pagination: { page, limit, total, totalPages, hasNextPage, hasPrevPage } }`
2. `POST /api/tasks` — create. Body: `{ title (required), description?, priority?, dueDate? }`.
3. `GET /api/tasks/:id` — single task detail.
4. `PUT /api/tasks/:id` — update provided fields only.
5. `PATCH /api/tasks/:id/status` — body `{ status }`; **the server only allows forward transitions `todo → doing → done` (one step at a time).** The UI must not offer an invalid transition.
6. `DELETE /api/tasks/:id` — delete.

Errors: `{ success: false, message, statusCode, details: [...] }` — the UI must surface readable messages including the `details` list, never raw JSON.
### 3. Recommended tech stack (choose one and justify)

Align with a modern JS ecosystem. Preferred primary recommendation: **React + TypeScript + Tailwind CSS** (optionally with a component library like Shadcn/Radix). A strong alternative is **Next.js (App Router) + Tailwind**. Consume the API with `fetch` or `axios`.

Suggested folder structure:

```
src/
  components/     (TaskCard, StatusBadge, PriorityBadge, Modal, Pagination, Filters, Toast, Confirm)
  services/       (typed API client — one function per endpoint)
  types/          (Task, API response / pagination / error types)
  hooks/          (useTasks, useCreateTask, useUpdateTask ...)
```

Every endpoint must be backed by a typed client function, e.g. `taskService.getAll({ status, priority, search, page, limit, sortBy, order })`, `taskService.create(payload)`, `taskService.updateTask(id, patch)`, `taskService.updateStatus(id, status)`, `taskService.remove(id)`.

### 4. Design language / visual direction

- **Tone:** a clean productivity tool, in the spirit of modern todo / project apps (Linear, Todoist, Asana).
- **Layout:** top app bar (logo + search field + "New Task" primary button) + a main content area. Use a responsive single-column layout that scales from mobile (stacked list) to desktop (table / card grid or kanban board).
- **Status colors:**
  - `todo` → neutral gray, outlined style
  - `doing` → blue / amber (active state)
  - `done` → green (or a struck-through checkmark)
- **Priority colors:**
  - `low` → gray / green, subtle
  - `medium` → amber / orange
  - `high` → red / rose (highlighted badge)
- **Style defaults:** soft backgrounds, rounded cards (`rounded-xl`), relaxed but spacious spacing, subtle shadows, strong text contrast.
- Provide a **design token table**: color (primary, background, surface, border, text, success, warning, danger), typography font stack + size scale, spacing scale, radius scale, shadow scale.
- **Empty state:** when there are no tasks / no results, show a friendly empty state with a clear "Create first task" action.
- **Loading & feedback:** show skeleton cards / spinners; disable submit while a request is pending; use toast notifications for success and error.

### 5. Screens & components to generate (full specification for each)

**A. Dashboard / Task List (main screen)**
- Header with a search input (debounced, server-side search → `search` param).
- Filter bar: selects for `status` and `priority`, a sort control (`sortBy` + `order`), and a "Clear filters" button.
- Display modes: **table / card list / kanban board** (choose one primary, mention one secondary).
- Each task row/card shows: title, priority badge, status badge, due date (highlight overdue in red), a short description snippet, and row actions (Advance status, Edit, Delete).
- Pagination footer using the `pagination` field from the API: previous / next, "Page X of N", and a page-size selector (`limit`).
- "New Task" button opens the create modal.

**B. Create / Edit Task Modal**
- Fields: Title (required, real-time validation), Description (textarea), Priority (select), Due Date (date/datetime input), Status (edit mode only).
- On submit: `POST /api/tasks` (create) or `PUT /api/tasks/:id` (edit). Handle field-level validation errors from `details`.

**C. Task Detail view**
- Full task info; editable `title`, `description`, `priority`, `dueDate`; inline status-advance control (forward-only); delete action with confirmation.

**D. Status advance interaction**
- Show an "Advance to Doing"/"Advance to Done" button **only when the next state is allowed**; after `done`, show no advance action. Guard the action with a confirm where appropriate.

**E. Delete confirmation**
- A modal or inline confirm: "Are you sure you want to delete 'X'? This cannot be undone." → `DELETE /api/tasks/:id`.

**F. Notifications / toasts**
- Success and error toast messages for every mutation, pulling the message text from API responses.

### 6. Interaction & accessibility spec

- All primary actions reachable by keyboard (focus states, logical tab order).
- Every form input is labeled; validation errors appear under the failing field (from the API `details` array when available).
- Show loading indicators (spinner / skeleton), disable confirm buttons while a request is in flight, and handle the empty-search / no-results states.
- Responsive breakpoints: mobile < 640px (stacked list), tablet 640–1024px (card grid), desktop > 1024px (table / grid / kanban).

### 7. Wiring map (screen → endpoint)

| Screen / action            | HTTP call                           |
| -------------------------- | ----------------------------------- |
| Load task list             | `GET /api/tasks` + query filters    |
| Search / filter / paginate | `GET /api/tasks` with query params  |
| Create task                | `POST /api/tasks`                   |
| Save edit                  | `PUT /api/tasks/:id`                |
| Advance status             | `PATCH /api/tasks/:id/status`       |
| Delete task                | `DELETE /api/tasks/:id`             |
| View detail                | `GET /api/tasks/:id` (or reuse list data) |

### 8. Output format — produce

1. Brief product + experience summary.
2. Page / screen sitemap.
3. ASCII or HTML wireframe for **each** screen (list, create/edit modal, detail view, confirm dialog).
4. Complete component inventory (card, badges, buttons, inputs, select, modal, toast, confirmation dialog, pagination, skeletons).
5. Full design tokens (colors, typography, radius, shadows, spacing).
6. Chosen tech stack + a **typed API client** code sketch (service layer) mapping to the contract above.
7. Implementation rundown / acceptance criteria checklist.

Deliver the entire response in **English**, structured with clear Markdown. Be concrete: include real type definitions for the service layer and be specific about visual hierarchy and spacing. Do **NOT** invent API fields, `status` values, or endpoints beyond the contract.
